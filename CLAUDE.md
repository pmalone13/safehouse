## How you got invoked, and how this session actually works

**Redesigned 2026-10-30, live session with Paul** — supersedes the old
"resume ticket" design described in this section before this date (that
design is gone: no `session_state` table, no `--resume` between
separate spawns, no coordinator-run wrap-up turn). The problem it
replaced: a resume ticket only let a *later, separate* spawn pick up
prior context — every queued message still got its own full spawn, its
own reply, its own commit/push/Drive-sync, which is exactly what made a
backlog (several messages piled up, e.g. after an outage, or just a few
texts sent close together) show up to Paul as a burst of separate,
individually-committed replies instead of one coherent response.

You were spawned by `coordinator.py` because a message arrived on the
FIFO queue (email, text, or `cron` — all live). The message that
triggered this turn is described in your prompt. **You are now expected
to stay alive and keep handling further messages yourself**, rather than
finish this one and stop, for as long as the protocol in step 4 below
says to. `coordinator.py` itself stays dumb: it claims one message,
spawns you, and waits — however long you run — before it'll ever claim
another. That's deliberate: while you're alive, nothing else gets
spawned, so a message that arrives mid-session is safe to self-claim
yourself (via the same `queue_db.claim_next()` the coordinator itself
uses) with zero risk of the coordinator also grabbing it.

Once you (or a future turn) actually decide to stop — per step 4 — that's
final: there is no ticket, no resume. The *next* message, whenever it
arrives, starts a genuinely fresh session with empty context. Any
continuity across a lull shorter than the windows in step 4 comes
entirely from this one process having stayed alive, not from anything
being remembered afterward.

  added to `EXCLUDE_NAMES`, or real binary-upload support (see below);
  application code, needs Paul live. **Standing lesson**: a manual
  "don't sync this" note in a project file isn't durable on its own —
  get it into `EXCLUDE_NAMES`, or store the file somewhere
  `drive_sync.py` structurally can't reach (e.g. outside this repo
  entirely, the approach used for later trip-photo archives).

- **`drive_sync.py` silently corrupts binary files.** It reads every
  file as UTF-8 text (`read_text(encoding="utf-8", errors="replace")`)
  and uploads it as `text/plain`, so any non-text file (.docx, .pdf,
  image, .zip) lands on Drive unopenable, with no error — the sync
  reports success. Verified 2026-09-03 against an alliecar `.docx`:
  31,060 bytes local vs 53,503 on Drive, 11,425 replacement chars,
  `BadZipFile` on open; the header bytes survive so it still looks fine
  in a Drive listing. Since everything under `projects/` is gitignored
  *on purpose* (Drive is meant to be the durable copy), a binary file has
  **no durable copy anywhere** except local disk. If Paul sends a
  binary, extract its content to a text sibling and say so rather than
  assume the mirror has it — same pattern already used for the alliecar
  doc and for sensitive files stored outside this repo entirely. Fixing
  the sync to do a real binary upload is a small change to
  `drive_sync.py`/`google_client.create_file()` — needs Paul present.

- **A live SSH session and the autonomous email-monitor/coordinator
  pipeline are NOT mutually exclusive** — found 2026-10-14. They can
  process the same inbound email at the same time (Paul emailed a test
  while SSHed in; the email-monitor queued it independently and the
  coordinator spawned its own session that also acted on it), and worse,
  **both share the same literal working directory and git repo on
  disk** — a live session's uncommitted edits can get swept up and
  committed under a different session's commit message by that other
  session's own `git add -A`. Harmless so far (an idempotent file save
  got duplicated once), but this is a real race for anything that fires
  a device/world action twice, or for a file mid-write when another
  session's checkpoint runs. Needs an actual architecture decision (a
  lock/mutex, or a dedup mechanism keyed on message content) that only
  Paul can make live — not something to patch unattended. Full detail:
  `projects/engineering/secure-agent-communication/CLAUDE.md`'s
  2026-10-14 ~02:5xZ entry.

- **`ted_protocol.poll_for_reply()` can return a stale reply as if it
  answered the command just sent** — found 2026-10-12 (queue id 275). It
  only checks whether a decryptable Bayhouse attachment is new to *this
  call's own* `seen_ids` set, never whether its timestamp is actually
  newer than the command just sent. Caught live: sending `STATUS` and
  polling returned an hours-old `PONG` as if it were the real answer.
  **Workaround until fixed**: query Gmail directly for `internalDate`
  newer than the send time instead of trusting the helper — do this for
  any future `send_command`+`poll_for_reply` use. Real fix (track a
  high-water-mark timestamp/message id, or compare `internalDate` inside
  the function itself) needs Paul live.
